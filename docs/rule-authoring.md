# 规则编写指南

规则是版本化、可解释的检测条件。规则评估的输入是 `NormalizedEvent` 和调用方提取的 IOC 候选值，输出是带规则版本、事件指纹和 evidence 的 `RuleHit`；没有命中时返回空结果，不静默生成告警。

## 规则元数据

每条规则需要：

- 稳定的非空 `id`；
- 面向分析员的 `name` 和 `description`；
- 大于零的整数 `version`；
- 一个非空条件树。

修改匹配语义时递增 `version`，不要复用同一版本号表示不同条件。规则命中会携带该版本，便于案件回放和审计。

## 条件类型

| 条件 | 用途 |
| --- | --- |
| `EventKindIs` | 匹配进程、文件、网络、登录或持久化事件。 |
| `HostPlatformIs` | 限定 Windows、Linux、macOS 或其他平台。 |
| `SourceIs` | 限定 agent、Sysmon、auditd、Windows Event 或人工来源。 |
| `SeverityAtLeast` | 匹配不低于指定严重性的事件。 |
| `IocIs` | 在调用方提供的 IOC 候选值中寻找同类匹配。 |
| `All` | 所有子条件都必须命中。 |
| `Any` | 任一子条件命中即可。 |

`All([])` 和 `Any([])` 会被拒绝。条件树越具体，命中 evidence 越容易解释，也越不容易产生误报。

## IOC 规则

IOC 类型包括 IP、域名、URL、文件哈希、文件路径和进程名。构造 `Indicator` 时会按类型规范化：文本通常转小写，文件路径统一分隔符，文件哈希必须是受支持长度的十六进制值。

规则评估不会猜测事件中的任意字段。适配器或上层调用方应从事件中提取候选值，并将这些值传给 `evaluate_rule` / `evaluate_rules`；命中 evidence 会说明 IOC 类型和值。

## 关联与解释

规则命中先组成 `EventObservation`，再由 `CorrelationPattern` 声明有序规则序列和时间窗口。关联只接受同一主机、时间顺序正确且处于窗口内的命中，并生成稳定的 detection dedup key。

建议的编写顺序：

1. 先用事件类型、来源和严重性建立窄条件。
2. 再用 `All` / `Any` 增加必要上下文。
3. 对确实需要外部候选值的场景使用 `IocIs`。
4. 为规则命中检查 evidence，为跨事件场景增加关联窗口测试。
5. 对重复输入、正常输入和误报输入分别保留 fixture，确认规则没有静默扩大范围。

## 风险边界

风险评分只表示调查优先级，不代表执行授权。响应计划默认是 dry-run；规则作者不应在规则中编码删除文件、终止进程或隔离主机等副作用。
